# Northstar live app preview lab

This is an **isolated preview service**. The product app page now embeds its authenticated tenant preview in place of the old visible Screen viewer; the original viewer implementation remains in the repository. The private `/preview-lab` route remains a diagnostic surface. Two dedicated preview emulators (`emulator-5560` and `emulator-5562`) are separate from the three capture emulators (`5554`, `5556`, `5558`). Preview worker 2 serves tenant sessions one visitor at a time. Worker 1 remains reserved for local diagnostics.

This directory in the Northstar repository is the source of truth for the preview service. The older sibling `work/northstar-preview-lab` folder on the original Mac is a local working copy; use this tracked directory for future changes and deployments. APKs, service secrets, browser build output, and `node_modules` are intentionally excluded. The deployed host copy is `/opt/northstar/preview-lab`; the static viewer is `/srv/northstar-preview`.

## What works

The browser displays frames from the real Android app. Pointer taps and drags reach the emulator's gRPC touch service; mouse-wheel and trackpad scrolling become Android swipes. Typing and Back/Home reach only the preview emulator through ADB. The last frame stays visible while the next is drawn, and the browser reconnects automatically after a dropped socket. The phone defaults to a viewport-sized fit; Enlarge is optional.

A login screen is part of the app preview. Visitors can use or create **their own** app accounts on their isolated device. Northstar does not provide a shared login or copy its account credentials to the emulator. The visitor must click the phone before typing. Printable ASCII text, including shell punctuation and literal `%s`, is sent through a quoted Android input command; a direct emulator keyboard RPC was tested but silently failed to enter text on this headless AVD. Full device wipe at session end removes the guest's local app and browser state. Unicode typing, password-manager autofill into the canvas, and external OAuth/verification flows still need app-by-app testing. Do not capture or log visitor input.

The text path was verified end to end on a clean AntennaPod worker using only dummy input: the broker allocated worker 2, a WebSocket text message containing `Lab !@#$&%s` was acknowledged, the exact text appeared in Android's UI hierarchy, and the test session ended and requested a wipe. This is an input test, not a claim that third-party sign-in or account creation was completed.

Controls that need the device are disabled until a live frame arrives. If the browser loses focus or the control socket closes during a drag, the touch is released instead of leaving Android stuck in a pressed state. The local gateway rejects browser WebSocket connections from origins other than this lab page; a rejected-origin handshake returned HTTP 403 in the test. The local shell benchmark has no browser Origin header and can still connect when the device is free.

On 2026-10-01, this was exercised in Chrome: Wikipedia onboarding → Home → Search, text entry yielding search results, Back navigation, and a manual reconnect. All five emulators were later online together. The gateways and broker listen only on Hetzner's loopback interface, reached from this Mac over SSH forwarding.

This is a **two-device lab pool**, not the final multi-user preview service. The app picker requests a device by Android package through the loopback allocator; the allocator atomically claims a matching gateway lease. Each worker accepts one viewer. A second tab cannot watch or control a leased device. The local diagnostic browser keeps an unpredictable lease token in that tab's session storage, so reloading reconnects to the same session; the embedded tenant viewer keeps the token only in memory and sends it through the WebSocket subprotocol. An expired token cannot claim a newly wiped device. **End session** revokes the token, clears the displayed frame, and triggers a full `-wipe-data` emulator restart of that worker only. If a tab closes without ending, the detached lease expires after two idle minutes and triggers the same reset. A gateway restart on an already-served emulator also forces a clean boot rather than forgetting the lease and exposing the previous state. The next visitor waits for the cold boot, currently about two minutes on this shared host.

The gateway refuses to serve a device with any Android account and reinstalls the assigned app from a checksummed APK catalog. Wikipedia has three staged splits; AntennaPod is a staged APK from the official F-Droid distribution, version 3.12.2, SHA-256 `3f43a4337a693cdb49141afe06cb596e88c796009ed77bff51e9444ce2d1ebfc`. Neither worker uses Northstar or the visitor's signed-in credentials.

At release, the worker now writes only the last allowed Android package name to its service state directory. The next `-wipe-data` boot checks that name against its allowlist and stages that package directly from the checksummed catalog. This avoids installing the fixed default app and then replacing it when consecutive visitors choose the same app. The file contains no app data, credentials, or visitor identity. An absent or invalid hint falls back to the configured default; the account check and full wipe still run on every boot.

The 2026-10-02 tenant-worker check provisioned Wikipedia, ended the lease, and observed `last-package` contain `org.wikipedia`. After the wiped restart, the host log showed `Installed org.wikipedia`, worker health returned **ready** with Wikipedia, Android listed Wikipedia without AntennaPod, and the account list was empty. This removes the redundant app swap on a repeated Wikipedia preview; cold Android boot is still the main reset delay.

On 2026-10-02, the real Chrome app picker showed Wikipedia **In use** and AntennaPod **Ready** from the broker's live catalog. Selecting AntennaPod allocated worker 2 and showed its fresh Home screen. A second tab requesting AntennaPod received the occupied state and no frames. Reloading the first tab reattached to the same lease. Ending it blanked the browser canvas, restarted only `emulator-5562` with `-wipe-data`, and returned AntennaPod to Home with zero Android accounts. `emulator-5560` and the three capture devices stayed online. This verifies isolation and a clean handoff for these two apps; it does not prove arbitrary-app compatibility or production-scale capacity.

The flexible-worker test then requested Wikipedia while worker 1 was occupied. The allocator chose worker 2, removed its default AntennaPod package, verified Wikipedia's staged APK splits, and launched Wikipedia's first-run welcome screen. Android showed **only Wikipedia** and zero accounts. AntennaPod could not claim worker 2 while that lease was active. After ending Wikipedia and a wiped restart, AntennaPod again opened at its clean Home screen; Android showed **only AntennaPod** and zero accounts. A fake expired token was rejected without reserving the clean worker. Worker 1 and the capture devices stayed online throughout.

The worker installs a requested staged package from the private catalog. A one-minute host timer discovers packages installed for Android capture runs, stages only their APK splits and optional researched icon, verifies hashes, then atomically publishes catalog metadata. The tenant broker and worker reload that catalog without a code edit or restart. On 2026-10-02, fifteen assigned apps beyond Wikipedia were installed from Google Play on a signed-in **capture** emulator and staged. The tenant guest never receives that Google account or its app data. Linksta has 2/2 assigned packages staged, Graet 8/9, and Test 11/12; GRAET was intentionally skipped because its available Android build is incompatible with the emulator. LinkedIn and Spotify passed a signed tenant-session smoke test with a live frame and clean end. The other newly staged apps still need guest-launch checks before claiming individual compatibility. Tenant authentication and app-catalog scoping are active; there is still no audio or dedicated preview capacity. Each worker begins from a wiped guest with one app for that session. Do not expose ports 18080–18083 publicly.

Automatic staging begins when a capture run has an exact Android package ID and Google Play has installed it on its assigned capture device. A name-only tenant assignment does not contain enough information to fetch an installable build safely; it remains pending until an Android capture or an operator-provisioned package supplies that identity. Staging publishes installable files, not a guarantee that the app launches or permits guest exploration. The 2026-10-02 backfill exposed and fixed two live-switch issues: root-run staging now gives the private package directory to the preview-worker account, and the tenant broker waits for split-APK installation rather than abandoning an acquired lease after 30 seconds. Guest startup also waits for PackageManager and retries a transient install failure.

## Private tenant access gate

Northstar's unlinked `/preview-lab` route authenticates the visitor and calls `POST /api/preview/access`. That API resolves the visitor's tenant, intersects its `target_apps` assignments with the host's HMAC-protected live APK inventory, and signs a five-minute grant listing only permitted packages. An app assigned to the tenant needs no separate preview permission. Published browsing flows now record the Android package identity; legacy releases without that field retain name matching. The former `preview_app_entitlements` switches were removed; their database table is unused. Assigned apps awaiting APK provisioning are shown as pending.

The private page passes the grant to its cross-origin viewer using origin-checked `postMessage`, never a URL. The tenant broker runs on loopback port 18083, verifies the grant before catalog or allocation, and admits only worker 2. A separate broker-to-worker secret prevents direct session creation. Caddy serves `/preview/` over HTTPS and proxies only the tenant broker and worker 2's authenticated WebSocket stream; ports 18080–18083 remain loopback-only. The worker lease travels in the WebSocket subprotocol. The local diagnostic broker and worker 1 remain separate. Server secrets are in `/etc/northstar-preview/` with group-restricted permissions. `Caddyfile.tenant-preview`, `workers-tenant.json`, and the tenant systemd units in this directory are the deployable configuration.

A signed integration smoke test denied unsigned catalog access and unauthorized AntennaPod allocation, then allocated Wikipedia, received a real frame, and ended the lease. In real Chrome, the visitor navigated onboarding, Home, Search and Back. On 2026-10-02, the Test tenant's delivered Wikipedia app automatically appeared on this private route; the visitor progressed from fresh onboarding to Home, Search, a Moon article, scrolled the article, returned with Back, and reconnected without losing the search state. The live viewer ranged roughly 12–24 painted frames/s and recent input-to-frame readings were about 106–367 ms on the shared host. Ending the session showed **Ended**, then worker 2 returned to ready with no account. The broker now also offers token-authorized session release when the video WebSocket is disconnected, while the worker only accepts broker-authenticated HTTP release in tenant mode. The product page uses this service, while testing of a second real tenant account, login-gated apps, more devices, and latency under concurrent load remains outstanding.

## Architecture

```
Chrome on Mac → local static test page → SSH loopback tunnel
  → app allocator (127.0.0.1:18082)
    → worker 1 gateway (127.0.0.1:18080) → emulator-5560 / gRPC 8554
    → worker 2 gateway (127.0.0.1:18081) → emulator-5562 / gRPC 8555
```

Google's Android Emulator WebRTC gateway was tested first. Its signaling connected, but this host/browser combination produced a black 2×2 media placeholder and then disconnected. The emulator's `streamScreenshot` gRPC method later stalled after a few frames. The current gateway polls `getScreenshot` at 540 × 1200 and targets 20 frames/s, encodes raw RGB frames as JPEG through the host's `/usr/bin/ffmpeg`, sends the newest frame to the active viewer, and discards stale frames. The viewer allows at most four frames in flight and acknowledges frames after drawing or discarding them; this prevents an unbounded backlog while covering the Hetzner round trip. The browser decodes only its newest pending frame and reconnects if frames stop. Wheel events are coalesced and sent as short Android swipes, with the next swipe waiting for the prior one to finish. Upstream protocol sources are pinned in `vendor/` for reproducible builds; Google code is under Apache 2.0 (license included).

The preview emulators use `-gpu lavapipe`. With the previous `swiftshader_indirect` mode, System UI repeatedly failed to complete startup even while the gateway was stopped. A cold boot with lavapipe avoided that failure. With the polling gateway, a 90-second socket soak received 1,758 frames (median frame gap 50 ms, p95 60 ms, maximum 249 ms), and the emulator and gateway remained active without a new System UI ANR. This is a short lab test, not a production reliability result. Both app streams reached roughly 19–20 frames/s concurrently, but the shared eight-logical-CPU host load exceeded 8 in that test. Dedicated preview capacity is still needed for predictable latency and more visitors.

With single-frame acknowledgement, the Mac-to-Hetzner tunnel delivered only 46 frames in 10 seconds. With the four-frame window and smaller JPEGs, the same test delivered 196 frames in 10 seconds (median frame gap 50 ms, p95 86 ms; median frame size 73 KB). Chrome showed roughly 20 frames/s while tapping, typing, scrolling, using Back, and reconnecting. Recent simple actions measured 122–232 ms from input to the next painted frame; launching a new app screen can take longer. These figures describe this one lab device and connection, not a production service-level guarantee.

For a repeatable Mac-to-host throughput check, close the Wikipedia preview browser tab temporarily, run `benchmark_stream.mjs` with Node.js 22 or newer (for example `node benchmark_stream.mjs 10`), then reopen the tab. Each worker admits only one viewer. The script reports frame rate, frame-gap percentiles, and median frame size over the same SSH tunnel used by Chrome.

`app_catalog.py stage PACKAGE --serial SERIAL` copies only APK splits from an installed app into the private host catalog and records checksums. `app_catalog.py install PACKAGE --serial SERIAL` verifies those checksums, installs the splits, and checks that Android reports the package. Wikipedia is staged as three APKs. Every preview-emulator service start now wipes user data; the gateway waits for Android to boot, rejects a nonempty account list, installs the staged app, applies headless input settings, and launches it before serving viewers. The wipe removes app data and settings, so sessions cannot yet be resumed across a preview-device restart. Do not use capture emulators as preview devices.

A controlled emulator-service restart was tested after enabling `Upholds=` and `BindsTo=` in the systemd units. The gateway stopped and returned automatically after the wiped emulator booted, with zero accounts, three Wikipedia APK splits, and no new System UI ANR. The browser reconnected without a manual refresh. Initial cold boot and installation took about two minutes on this loaded host, so this is a recovery path, not a fast per-visitor reset. The lab header uses the Wikipedia icon extracted from the staged APK rather than a generic letter.

The preview emulator lacks a Bluetooth packet streamer; its Google Bluetooth process showed a crash dialog after a cold boot. Startup now disables that package only on this preview AVD, dismisses the dialog, and launches Wikipedia. A subsequent wiped cold boot reached the app with no modal and no System UI ANR. Bluetooth-dependent apps will need a compatible device configuration; this workaround is not applied to the three capture emulators.

All five currently running emulators use ADB-only text input. `prepare_headless_input.py` disables Gboard, the Google Search/Assistant app, and Google TTS for Android user 0, and clears the IME, voice, and Autofill services. It leaves Google Play and Play Services installed. Run it only while selected devices are idle. The `--reboot` option reboots each device and reapplies the settings after Android finishes booting because an early boot can restore the system packages. The prior preference-only helper, `configure_emulator_input.py`, was insufficient to suppress Gboard's floating toolbar.

On Hetzner, for a new or rebooted idle emulator:

```bash
python3 /opt/northstar/preview-lab/prepare_headless_input.py --reboot emulator-5554
```

Use `emulator-5556`, `emulator-5558`, `emulator-5560`, or `emulator-5562` for the other devices. The script verifies disabled package state, Autofill, and the Play Store package. ADB text entry was checked in Wikipedia with no IME showing; Google Play opened on `emulator-5554`, but a new app installation was not tested after this change. Android guest boot can restore the packages. The `northstar-headless-input.timer` checks the three capture devices and Wikipedia preview once per minute and reapplies settings if needed; AntennaPod's gateway applies the same settings on every wiped boot. The timer skips offline or booting devices and does not send Back during automatic repair. The unit and timer files are kept beside the helper in this lab. To restore normal input on a device, disable this timer first, run `adb -s SERIAL shell pm enable` for each of the three disabled packages, then reselect Gboard in Android's keyboard settings and reboot.
For a read-only check of all five, run `python3 /opt/northstar/preview-lab/prepare_headless_input.py --check emulator-5554 emulator-5556 emulator-5558 emulator-5560 emulator-5562`.

The service reads the emulator discovery token at runtime and never sends it to the browser. `emulator_access.json` is a copy used **only** by this preview emulator, allowing its authenticated gRPC streaming method without changing the global SDK access list or capture devices.
