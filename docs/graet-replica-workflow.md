# GRAET simulator page standard

This app follows the [app simulator preview standard](app-simulator-preview-standard.md). Use the [page-family build sheet](app-simulator-family-template.md) when starting each new family or app.

Use the current GRAET tenant capture set in `public/graet-replica/tenant-source` as the visual reference. Work on one screen family at a time. The next family starts only after the current family passes the checks below.

1. **Inventory:** List the first, middle, and final capture for the family. Record every visible row, button, tab, scroll continuation, and destination. Mark content missing from the captures before coding it.
2. **Component:** Build one shared layout for repeated entities. Feed it captured names, scores, images, and labels. Simulated details may fill uncaptured destinations, but keep them separate from captured facts in the data model. Do not replace a captured default state with an invented visual state when adding mock behavior; put uncaptured outcomes in a clearly separate view until a tenant capture establishes their design.
3. **Visual review:** Render at the 375 × 812 phone viewport. Compare the running screen beside the tenant captures at the top, middle, and bottom. Inspect logo centering, typography, spacing, alignment, sticky elements, overlays, clipping, and bottom navigation. Correct the differences before moving to another page.
4. **Interaction review:** Click or swipe every visible control. Check the destination, selected state, horizontal and vertical scrolling, back navigation, and restored scroll position. Recheck the visual state after each interaction.
5. **Exit gate:** Typecheck and lint the changed files, then record which views were visually reviewed and which remain simulated or uncaptured in `graet-replica-audit.md`. A working click or a passing build alone does not mark a screen complete.

For Player Profile, inspect captured media crops before adding HTML labels: a screenshot can already contain names, flags, counts, action rows, or the next section. Keep each visible label in exactly one layer. Open hero and post option sheets from a top, middle, and lower scroll position, then dismiss them and confirm the same content remains in view. Test Thomas, a grid player with a captured card photo, a player without a profile photo, a related-player card, and the Profile tab through the same component.

For Games, league and match records live in `components/preview/graet-game-data.ts` and render through shared components. Mark invented records `source: "simulated"` in that file. Captured logos remain image crops, while names and scores are HTML content. The Sparta–Karlovy Vary destination retains its exact captured frames; other match destinations use the same match page structure with simulated content for uncaptured details. Check at least two teams with different logo shapes to ensure the shared crop and alignment work across rows.

For Openings, cards and details share the records in `components/preview/graet-opening-data.ts`. Partially obscured card fields are listed in `simulatedFields`; the Minnesota detail and application capture are the visual baseline for the shared components. Check one card at the start, middle, and end of the list, then open two different teams and return to the same scroll offset. Submitting a mock application must update My applications and the selected opening action.

For Colleges, names, locations, and leagues are captured in `components/preview/graet-college-data.ts`; fields identified there as mock only serve uncaptured variants and filter behavior. Review the list at every screenshot join so a card or section is never repeated. The Hobart Overview and Academics captures are the baseline for school details. Open a top, middle, and final list card, visit both school tabs, scroll each from top to bottom, and return to the original list position. On the filter sheet, compare the state-chip rows and fixed footer against the tenant image, then test that Close discards draft edits, Clear all only clears the draft, and Apply changes the results. Save and cancel notes, reopen them, and verify the displayed note is editable.
