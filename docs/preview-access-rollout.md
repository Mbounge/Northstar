# Preview access rollout

The interactive Android preview remains on the private `/preview-lab` route while we validate it; the existing Screen viewer stays in the product. **An app already assigned to a tenant in `target_apps` needs no second preview permission.** The preview access API intersects that tenant's app names with the Android packages provisioned in `lib/preview/staged-apps.ts`. An unassigned app is never included in a signed preview grant, even if its APK is on a worker. App names in this temporary registry must match the tenant catalog; a durable package ID on the app record is needed before automated provisioning and arbitrary app-scale rollout.

The former Admin → Tenant workspace “Preview lab access” panel and its write API were removed because their independent switches could disagree with the tenant's actual app assignments. The old `preview_app_entitlements` database table is now unused; it has been left in place for a later controlled schema cleanup. Existing rows in that table cannot grant preview access.

`POST /api/preview/access` checks the signed-in user's approved `customer_id`, reads only that tenant's `target_apps`, and creates a five-minute HMAC grant for their provisioned apps. The browser never supplies the tenant or package list. `NORTHSTAR_PREVIEW_GRANT_SECRET` is configured in Vercel Production; do not log or return it.

The current provisioned registry is Wikipedia (`org.wikipedia`) and AntennaPod (`de.danoeh.antennapod`). This is narrower than Northstar's research catalog. An assigned app without a provisioned APK simply does not appear in the private preview. Keep the staged registry aligned with the lab's checksummed APK catalog and worker package allowlists. App provisioning must later replace the static registry.

On the Hetzner capture host, separate grant and broker-to-worker secrets live in `/etc/northstar-preview/` with `root:northstar` ownership and mode `0640`. Preview device 2 is behind a tenant-only broker on loopback port 18083. Caddy serves the isolated viewer at `/preview/`, routes signed catalog/allocation requests to the broker, and exposes only device 2's authenticated `/stream` over WSS. Public direct access to the broker and workers' loopback ports is blocked. The tenant emulator, gateway, reset watcher, broker, and Caddy are enabled at boot. Preview device 1 remains for local diagnostics; the three capture emulators are separate.

The viewer receives its grant through a checked `postMessage` from authenticated Northstar; the grant is never placed in a URL. The worker lease travels in the WSS subprotocol in tenant mode. The iframe has a `frame-ancestors` policy limited to Northstar and local development origins.

On 2026-10-02, the private route showed only Wikipedia under the prior explicit Graet assignment. In the real Chrome profile, the visitor reached Wikipedia's onboarding, Home, Search, account creation and login pages, and could tap, scroll, use Back, and enter test text without submitting credentials. Ending the session showed a stable Ended state and triggered a full `-wipe-data` reset; the worker returned healthy and available. Switching that same signed-in profile temporarily to the Test tenant showed no apps; granting AntennaPod through the old panel showed only AntennaPod and opened a live private device. That temporary grant was removed and the profile restored to Graet. This tested tenant scoping but did not test two independent users. The signed-in tenant must be retested after this change using actual `target_apps` assignment.

Before replacing Screen viewer, test two independent tenant accounts, concurrent visitors and queueing, a global/shared app policy through the product's own app-assignment model, unauthorized allocation rejection, and a full wipe before the next visitor. Confirm a login-gated app can be explored with the visitor's own account; Wikipedia's form was reached but a real login was not submitted. Frame rate varied during the run and the host reached load averages near or above its eight logical CPUs with the capture and preview emulators together. Plan preview capacity separately from capture capacity rather than treating this single worker as scalable production capacity.
